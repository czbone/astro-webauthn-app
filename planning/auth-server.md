# 認証サーバー

本ファイルは、利用権限について認証サーバーが行うことです。実効権限は [grant.md](grant.md) の手順だけを使います。ログイン、パスキー、招待、ユーザー作成は今のとおりです。

## スキーマ

認証サーバーがマイグレーションします。参加アプリはマイグレーションしません。

```sql
ALTER TABLE "App" ADD COLUMN "defaultPermission" TEXT;
```

既存のアプリは空のままです。行が無い利用者は、既定を書くまで入れません。既存の `AppGrant` はそのまま有効です。利用者全員への埋め戻しはしません。

`AppGrant.userId` は必須のままです。外部キーと `(userId, appId)` の一意制約は変えません。利用者を削除すると、その利用者の行だけが消えます。アプリを削除すると、そのアプリの行が消えます。既定は `App` の列なので、利用者の増減では変わりません。

## 書くときの検査

管理画面が保存するとき、次だけを受けます。

| 列 | 受け付ける値 |
| --- | --- |
| `App.defaultPermission` | 空、または [grant.md](grant.md) の正の権限 |
| `AppGrant.permission` | 正の権限、または `none` |

`none`、空、一覧に無い文字列は既定に保存しません。正の権限でも `none` でもない値は、行に保存しません。データベースの制約では名前を固定しません。名前を足すときは、保存の検査と [grant.md](grant.md) の一覧を同時に更新します。

## 引き渡し

`GET /auth/handoff` でセッションを作る条件のうち、付与の確認を実効権限に置き換えます。他の条件は [multi-app-auth.md](https://github.com/czbone/astro-user-webauthn2/blob/main/planning/multi-app-auth.md) のとおりです。

```text
認証サーバーのセッションを検証
Credential が 1 件以上
実効権限が正の権限
redirect_uri が App.redirectUris と完全一致
```

実効権限が付与なしのときは、セッションを作らず、参加アプリへ戻しません。応答は 403「引き渡し先のアプリを利用できません」です。`none` の行がある利用者も、既定が空で行が無い利用者も、同じです。

セッションの JSON には権限を入れません。

## 管理操作

アプリの登録と変更で、既定を空または正の権限に一度設定します。既定を `admin` にすると、行が無い利用者もそのアプリの管理者になります。

行を作るのは例外だけです。

| 操作 | 結果 |
| --- | --- |
| 既定を `user` にする | 行が無い利用者は利用者になる。次のリクエストから効く |
| 既定を空に戻す | 行が無い利用者は入れなくなる |
| `admin` の行を一枚作る | その利用者だけ管理者になる |
| `none` の行を一枚作る | その利用者は既定があっても入れない |
| 行を消す | その利用者は既定に戻る。既定が空なら入れない |
| 利用者を追加する | 行は作らない |
| アプリを追加する | そのアプリの既定を一度決める。既存利用者の行は作らない |

同じ利用者とアプリの組に、行を二枚は作れません。

## 認証サーバーの role

`User.role` は、招待と `App` / `AppGrant` の編集など、認証サーバー自身の権限です。名前が増えても、実効権限の入力にはしません。`role` を変えても、既定と行を書き換えない限り、参加アプリの権限は変わりません。

seed 管理者にも、アプリの `admin` は自動では付きません。既定が `user` のアプリには、行が無くても利用者として入れます。
