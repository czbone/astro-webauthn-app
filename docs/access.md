# 権限とアクセス制御

参加アプリは、画面を表示する前に、セッション、ユーザーの有効状態、パスキー、実効許可の順に確認します。実効許可が `allow` の場合に限り、入場できます。`User.role` は入場判定には使わず、入場後の画面分けに使います。共通 `admin` であっても、実効許可が `allow` でなければ、このアプリを利用できません。

実効許可の判定方法は [grant.md](../planning/app-permissions/grant.md) に記載されています。`App` が存在しない場合、`AppGrant.permission` が `allow` 以外の場合、または行がなく既定値も `allow` でない場合は、許可されません。`admin` や `user` という文字列は、行または既定値に設定されていても許可として扱いません。行がある場合、既定値による判定には進みません。

許可の付与と変更は、認証サーバーだけが行います。許可の取り消しや `permission` の変更、ユーザーの無効化は、次のリクエストから反映されます。セッションを作り直す必要はありません。

このアプリに公開パスはありません。未ログイン時は引き渡しを開始し、このアプリの本文は表示しません。`/callback` と `/logged-out` では引き渡しを開始しません。

手動での確認手順は [verification.md](verification.md) を参照してください。仕様は [participant-app.md](https://github.com/czbone/astro-user-webauthn2/blob/main/planning/participant-app.md) と [app-permissions](../planning/app-permissions/README.md) に記載されています。

## 判定の順序

`__Host-session` の値を SHA-256（hex 小文字）にし、`sess:{APP_ID}:{tokenHash}` を読みます。実際の Redis キーには `REDIS_KEY_PREFIX` が付きます。

```text
Cookie が無い
  → 未認証。Cookie は消さない
セッションが無い、JSON でない、appId が APP_ID と違う、userId が空
  → キーがあるときは削除し、userId があれば索引から外す。Cookie を消して未認証
User が無い（id, email, name, role, disabledAt を引く）
  → 自分のセッションを削除し、索引から自分の要素を外す。Cookie を消して未認証
disabledAt がある
  → 索引に含まれる全セッションと、今のセッションと、索引を消す。Cookie を消して未認証
WebAuthnCredential が 0 件
  → パスキー未登録。TTL も Cookie も延ばさない
実効許可が allow 以外
  → 付与なし。Cookie は残す。TTL も Cookie の Max-Age も延ばさない
ここまで通ったとき
  → 画面ではセッションの TTL と Cookie の Max-Age を延ばす
```

索引の要素は `{appId}/{tokenHash}` です。壊れたセッションやユーザー行が無いときは、自分の要素だけを外します。ログアウトと、無効ユーザーの解決では、索引から得た他アプリのキーも消し、索引自体を消します。

## 画面

GET と HEAD だけが画面です。`/callback`、`/logged-out`、ファイル名に `.` を含む静的ファイルは、セッションがなくても引き渡しを始めません。

| 解決結果 | 画面 |
| --- | --- |
| 未認証 | `{AUTH_ORIGIN}/auth/handoff` へ 302。ログイン画面は出さない |
| パスキー未登録 | `{AUTH_ORIGIN}/setup-passkey` へ 302 |
| 付与なし | 403「このアプリを利用する権限がありません」。操作はヘッダのログアウトだけ |
| 実効許可が `allow` | 共通ロールでページを描く |

`/` にはメールアドレス、名前、共通ロールを表示します。ロールの表示名は、`admin` が「管理者」、`manager` が「ユーザー管理者」、`user` が「一般ユーザー」です。利用許可は「利用可」と表示します。

ヘッダの「利用許可の例外」は共通 `admin` だけに出します。「アプリ内ロール」は共通 `admin` または `manager` に出します。`/` の本文には置きません。セッションがあるヘッダは「ログアウト」（`POST /logout`）を出します。`/logged-out` のヘッダは「ログイン」で、リンク先は `/` です。このページから引き渡しは始めません。

`/grants` は、共通ロールが `admin` のときだけ一覧を読みます。列はメールアドレス、名前、利用許可で、メールアドレスの昇順です。`allow` は「利用可」、`none` は「利用不可」です。一覧の先頭に既定を出します。既定が `allow` のときは「全利用者に利用を許可」、`NULL` のときは「利用を許可しない（個別のみ）」です。それ以外の既定は「設定エラー。既定からは入場させない」です。既定だけで入っている利用者は出しません。行が無いときは「例外の付与はありません」。変更操作は置きません。それ以外の共通ロールは 403「この画面を利用する権限がありません」で、`/` へのリンクを出します。この拒否は入場を確認したあとに行うので、セッションの TTL は延ばします。

`/roles` は、共通ロールが `admin` または `manager` のときだけ開きます。このアプリは業務操作を持たないので、割り当て可能なアプリ内ロールはありません。画面は「割り当てられるアプリ内ロールはありません」と出します。更新口は置きません。共通 `user` は 403「この画面を利用する権限がありません」で、`/` へのリンクを出します。この拒否でも TTL は延ばします。ロールを足すときは `public` 以外のスキーマに `User.id` をキーにして置き、そのスキーマだけこのアプリがマイグレーションします。`AppGrant` には書きません。定義が無いあいだ、更新は `POST /logout` だけです。

更新リクエストでは引き渡しを開始しません。未認証の場合、更新リクエストには 401「ログインが必要です」を返します。

## 更新

POST、PUT、PATCH、DELETE は、`Origin` が `APP_ORIGIN` と完全一致するときだけ受けます。`Origin` が無い、または一致しない更新は 403「オリジンが不正です」です。他オリジン向けの `Access-Control-Allow-Credentials` は返しません。

通す更新は `POST /logout` だけです。それ以外は、セッションがあっても 404「見つかりません」です。パスキーが無い更新は 403「先にパスキーを登録してください」、付与が無い更新は 403「このアプリを利用する権限がありません」です。ログアウトはこの 403 の対象外です。

ログアウトは、許可がないセッションやパスキーが 0 件のセッションでも実行できます。`userId` は自分の `sess:{APP_ID}:{tokenHash}` から読み取り、`SMEMBERS sess:user:{userId}` で得た各セッションを削除したうえで、現在のセッションと索引も削除します。`__Host-session` と `__Host-handoff` を削除し、`/logged-out` へ 303 でリダイレクトします。認証サーバーへの HTTP リクエストは行いません。無効なユーザーは、アクセス解決時に全セッションが失効して未認証となるため、ログアウトの応答は 401「ログインが必要です」です。

## 参照するデータ

PostgreSQL は次の列だけを参照します。

| テーブル | 参照 |
| --- | --- |
| `User` | `id`、`email`、`name`、`role`、`disabledAt` |
| `WebAuthnCredential` | 件数（`id` と `userId`） |
| `App`、`AppGrant` | 参照。このアプリが書くことはない |

`User.password`、パスキーの公開鍵、カウンタ、`credentialId`、`transports` は読みません。例外一覧の SQL は、共通ロールが `admin` のときだけ実行します。
